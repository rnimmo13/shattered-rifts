# Review: Riftwalker id rename (DECISIONS #190) and the Brass Cascade elite event

Scope: working tree against 836eeab. `pnpm lint`, `pnpm typecheck` and `pnpm test` all pass (45 files, 2451 tests). Nothing was edited.
There are no CRITICAL findings. Old-id handling is correct everywhere it was wired. The gaps are one cost problem on the server, a stale
generated doc, and some edge-case robustness issues in the Cascade.

## CRITICAL
None.

## HIGH
None.

## MEDIUM

### M1. Leaderboard constructor migration scans five whole tables every time the Durable Object starts
`apps/server/src/board.ts:148-160`
The `UPDATE ... WHERE col IN (...)` statements run on every construction, not once. A Durable Object is constructed again after every
hibernation or eviction. None of `winner_hero`, `loser_hero`, `hero` (runs), `hero` (ghosts) or `human_hero` is indexed, so each
wake-up reads every row of `pvp`, `runs` (queried with `LIMIT 20000` elsewhere, so it can be large), `ghosts` and `ghost_games`.
Cloudflare bills SQLite DO rows read.
Failure scenario: the board DO wakes about once per idle gap. Each wake reads the full history of every table to change zero rows,
for as long as the code stays.
Fix: guard it with a one-time flag. For example `if (!ctx.storage.kv.get('hero-ids-190')) { ...rename...; ctx.storage.kv.put('hero-ids-190', 1); }`,
or a row in a meta table.
Correctness and injection are fine. The SQL is built only from the constant `LEGACY_HERO_IDS` (fixed lowercase literals), with no user
input. The table and column names are literals at the call sites. The CASE and WHERE logic is right and idempotent. All five tables and
columns exist, and the `CREATE TABLE IF NOT EXISTS` statements run before the migration.

### M2. `docs/10_CARD_LIST.md` is stale
`docs/10_CARD_LIST.md:1137-1148` ("Pool sizes") still lists `maren: 92 ... kp: 89`. `git diff --stat` shows the file untouched. The file is generated by
`pnpm cardlist` (`tools/src/cardlist.ts:51` prints `${h}` from `RIFTWALKERS` keys).
Failure scenario: anyone reading the roster doc sees the old ids, which contradicts DECISIONS #190 and `docs/09_ROSTER.md`.
Fix: run `pnpm cardlist`. `packages/content/src/v2/lanes.generated.ts` is keyed by card id, which did not change, so it is not stale.

### M3. A Cascade result is not recorded until the player presses "Choose"
`apps/web/src/trials/TrialHost.tsx:45-48, 82-101`; `apps/web/src/run/Pickers.tsx:583-585`
When the last ball lands, the host moves to the `result` stage ("You earned N prizes") but the run is still `state: 'playing'`.
`finishTrial` is only called from the Choose button.
Failure scenario: the player lands 3 good lanes, then the tab crashes, the connection drops or they reload on the result screen. On
load, `settleInterrupted` marks the trial failed, with no consolation, and the earned prizes are lost. This is consistent with "one
try", but it is harsh and surprising. Calling `onDone` automatically when the last ball lands, or persisting `earned` at that moment,
would avoid it.

### M4. The "Rift-crossed rares" lane can offer non-rare (or legendary) cards while its label says "rare"
`packages/campaign/src/trials.ts:105-106` calls `crossedOffers(... ['rare' x6], 6)`. `packages/campaign/src/rewards.ts:62-63` falls back to
`pool.filter(id => !out.includes(id))` (any rarity) when it runs out of rares. `crossedPool` was not checked for excluding legendaries.
The prize label and short text still say "Rift-crossed rares", `trials.ts:128-131`.
Failure scenario: a hero whose crossed pool has fewer than 6 unused rares gets a "choose a rare" lane containing commons, which is
mislabelled. Mixing rarities within one choice is also inconsistent.
Fix: filter to rares in `trials.ts`, or accept only `rarityOf(id) === 'rare'` and fall back to a purse otherwise.

### M5. A client can claim any lanes: `finishTrial(won, earned)` trusts the client
`packages/campaign/src/run.ts:873-883`; `packages/campaign/src/trials.ts:262-277`
`endTrial` only checks that the indices are in range, then sorts them and keeps the 3 lowest. The `seed` on the offer is never used to
replay or verify the drops. The ball wobble uses `Math.random` in the client, so it cannot be verified.
Failure scenario: a modified client, or console call, submits `[0, 9, 4]` and chooses the best prize. Runs are meant to feed the
Arena and the leaderboards ("verified runs" in docs/12). A run played this way would be unverifiable.
Also, a hostile client submitting 4 or more lanes silently has the highest-index ones dropped, which is harmless but arbitrary.
This is acceptable for the web version (the local save is already editable, and the export and import path allows retries). Note it in
docs/12 for the Steam "verified runs" requirement.

### M6. Held-key aim handling and global key capture
`apps/web/src/trials/Cascade.tsx:272-304`
- `keydown` listens on `window` and calls `preventDefault()` for `a`, `d`, `w`, `s`, Space and Enter, with no modifier check.
  Ctrl+S, Ctrl+D and Ctrl+A are swallowed while the game is open. Enter or Space also hits `drop()` even when focus is on an unrelated
  button.
- `held` is cleared only on a matching `keyup` for the same `e.key`. If Shift is pressed while `a` is held, the keyup is `A`, which `side()`
  does not map, so `held.left` stays true and the aim slides until the next drop. The same happens on window blur (Alt-Tab) while a key is down.
Fix: ignore events with ctrl, meta or alt; lowercase `e.key`; clear `held` on `blur`.

## LOW

### L1. Cascade effect restarts whenever the parent re-renders
`apps/web/src/trials/Cascade.tsx:253` has `useEffect(..., [prizes])`. `EventView` builds `prizes` with an inline `.map(...)`
(`Pickers.tsx:577`), and `TrialHost` passes it straight through. Any re-render of `EventView` (for example a `say()` notice) produces a
new array, so the loop effect is torn down and rebuilt. That recreates `wobble`, resets `last` and `acc`, and resets `cv.width` (which
clears and resets the canvas). The game state lives in refs, so play continues, but there can be a visible frame hitch. Fix: memoise
`prizes` in `EventView`, or read prizes through a ref.

### L2. No watchdog on a stuck ball
`apps/web/src/trials/physics.ts` and `Cascade.tsx`. If a ball ever fails to land (balanced on a peg, or wedged on a wall half-peg),
the game never ends and Begin is already spent. Reload settles it as failed, so it is not a soft-lock, but it costs the whole trial.
A time cap (for example 25 s, then force the nearest slot) is cheap. `simulateDrop` only guards its own 30 s loop.

### L3. `validTrial` accepts inconsistent states
`packages/campaign/src/save.ts:166-185`. It allows `state: 'won'` with `earned` missing or `[]`. `EventView` hides the options when `won`
(`Pickers.tsx:672`), and `takePrize` refuses with "You did not earn that one", so a hand-edited or corrupted save would be unable to
leave the event. Require `earned` non-empty with a length of at most 3 when `state === 'won'` (and perhaps each `earned` index below
`prizes.length`). Prize `card`, `boon` and `potion` display fields are also unchecked.

### L4. `parseRun` can throw on malformed input instead of returning null
`packages/campaign/src/save.ts:246-252, 267-275`. `for (const n of (r.map?.nodes ?? []))` throws if `nodes` is not iterable (for example a
number). `ev.options.filter` throws if a retired-trial event has no `options` array. The import path, `RunScreen.tsx:269`
(`await file.text()` then `parseRun`), would surface an unhandled rejection rather than "not a valid run save". Guard with `Array.isArray`
before the loops. Real saves are unaffected.

### L5. Legacy ghosts reappear once under a new id
`apps/server/src/board.ts:201`: `deckId` hashes `e.hero`, which is now canonical. An old ghost's hash includes the old id, so the same
player and deck registers a second ghost row. DECISIONS #190 already says this is accepted. The old row will age out through `last_at`
pruning. This matches the documented behaviour.

### L6. In-flight Arena rooms across the deploy
`apps/server/src/room.ts:97-108, 207-227`. A `MatchRoom` saved before the deploy holds `entries` with old hero ids. `rebuild()` replays
the log; with an unknown hero `arenaHp` gives `{}`, and the replay probably fails or desyncs. This is caught and the match ends as a
draw/disconnect, so it is not a crash. It is a one-time effect on matches in progress at deploy. Passing `entries.*.hero` through
`canonicalHero` before `new Match` would remove it.

### L7. Stale script names in comments
- `tools/pack-knight.ps1:3` still says "Run: powershell -File tools/pack-valeria.ps1" (the file was renamed).
- `tools/pack-heroes.ps1:5` has the same stale pointer.
- `docs/12_STEAM_READINESS.md:118` still points at `assets-src/valeria`, which is correct, but the DECISIONS #150 text mentions `pack-valeria`. That entry is historical, so it is fine.
- `pnpm cardscan -- --heroes` and `pnpm fight --hero` now require the new ids with no legacy mapping. This is only a CLI usability note.

### L8. One try can be sidestepped through exported saves
`RunScreen.tsx:269-275` (import) and localStorage copies can restore a pre-Begin save. This cannot be prevented client-side. It is
noted only because the UI promises "one try".

### L9. Pointer-up drop
`Cascade.tsx:333-337`: `onPointerUp` calls `drop()` for any button, including right and middle click, so a stray right-click drops a ball.
Check `e.button === 0` or `e.pointerType`.
